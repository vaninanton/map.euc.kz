# Скилл: обновление велодорожек Алматы

Данные велодорожек в `src/data/almaty.json` изначально были собраны из API
velojol.kz (см. комментарий в `src/types/velojol.ts`), но этот путь
(`velojol.kz/static/data/cities/almaty.json`) на 2026-07-29 отдаёт 404 — сайт
жив, эндпоинт с данными пропал. Поэтому источник правды для сверки —
**OpenStreetMap**, единственный стабильно доступный независимый источник.

## Шаг 1. Запустить сверку

```bash
node scripts/compare-bike-paths.js
```

Скрипт запрашивает Overpass API (velodorожки в bbox Алматы: `cycleway=*`)
и сравнивает геометрию с текущими сегментами `almaty.json`. На выходе два
списка:

1. **Возможно устаревшие** — конец текущего сегмента дальше 150 м от любой
   велодорожки OSM. Могли снести, переименовать улицу или дорожка сама себя
   изжила.
2. **Кандидаты на добавление** — велодорожка есть в OSM, но нет ничего похожего
   в `almaty.json` (сгруппировано по названию — OSM режет одну улицу на много
   `way`, без группировки список раздувается в разы).

Это **черновой геометрический скрининг, не автообновление**: `safetyLevel`,
`description`, `source`, `date` — поля ручные, их в OSM нет и никогда не
будет. Список — повод пойти и посмотреть глазами (Google/Yandex панорамы,
сама OSM-страница по ссылке из отчёта, при возможности — реальный выезд).

Для программной обработки (не для чтения человеком) — флаг `--json`,
печатает `{ stale, candidates }` в stdout.

## Шаг 2. Разобрать находки руками

Для каждого пункта из «возможно устаревшие»:
- Открой `almaty.json`, найди сегмент по `id`.
- Проверь по спутнику/панораме, жива ли дорожка в этом виде.
- Если снесли/изменили — обнови `coordinates`/`description`/`safetyLevel` или
  удали сегмент целиком (с объяснением в PR, почему).

Для каждого пункта из «кандидаты на добавление»:
- Открой ссылку на OSM way, посмотри, что это реально (иногда `cycleway=*`
  цепляет разметку вдоль тротуара, которая не тянет на отдельный маршрут —
  такое не добавлять).
- Если это настоящая велодорожка — добавь новый объект в `almaty.json` по
  схеме `VelojolSegment` (`src/types/velojol.ts`): `id` (следующий свободный
  `almNN`), `name`, `distance` (посчитать по координатам), `safetyLevel`
  (1–5, экспертная оценка, не из OSM), `description`, `coordinates` (пары
  `[lon, lat]`, из геометрии OSM way или уточнить руками), `source: "OSM"`
  (не `"Velojol"` — честно указывать происхождение), `date` (сегодняшняя).

Не переноси в `almaty.json` пачками без проверки — 140 «кандидатов» за один
прогон включают в себя как реальные новые дорожки, так и шум (велотрассы MTB
вроде «XCO Alatau», разметку не по теме). Смысл скрипта — сузить область
поиска, а не заменить проверку.

## Шаг 3. Оформить как PR

Дальше — по стандартному флоу этого репозитория, см.
[[git-feature-workflow]] (`.claude/skills/git-feature-workflow/SKILL.md`):
ветка `feature/update-bike-paths-<дата>` → коммит → push → `gh pr create`.

Commit message: `feat(map): обновить велодорожки Алматы по сверке с OSM`
(или `fix(map): ...`, если в основном чинили устаревшее).

В теле PR обязательно перечисли, что именно изменилось (какие сегменты
обновлены/добавлены/удалены и почему) — ревьюеру (Антону) сверять с картой
руками долго, а список решений — быстро.
